## 0. 目标定位

- 知识库 = 用户使用 agent 时的**第二大脑**,内容 90%+ 给 AI 读,默认不翻译
- **知识在于精不在于泛**:宁缺毋滥,fail-closed 贯穿全链
- 每篇 wiki 必须提供可执行的 **how**,知识与图谱共同给出"可行性方向"
- 领域:设计 / UI 设计 / 前端搭建 / AI 动画 / AI UI 动画 / 游戏设计 / AI Agent / Loop Engineering + 补充(Context Engineering / Harness Engineering / Eval 工程 / 多 Agent 编排 / AI 编码工作流 / 设计系统与 Token / 生成式 UI)
- 刻意不收:模型新闻、融资动态、benchmark 刷分、任何"新闻摘要桶"内容

## 3. 入库与升格机制(已拍板,颠覆原宪法两处)

- **取消逐条人批** → **五闸自动升格**:gate 10/10 + confidence high + real_link + lint 0 + GPT-5.4 复核 PASS,全过自动入 active,任一不过留 staging
- **需修宪**:CONTENT-STANDARD 不变量 3"没有自动 active"按修订程序改为五闸机器判定;Sync Impact Report 记录;Plan 1 内执行
- **每日入库量不设上限**;质量责任全压 gate(硬判定 pass/fail,无排序打分)
- 双轨试运行:前 50 条自动入库留快照供抽查,误放一键回滚
- **score 连续分数体系废除**:入库用硬判定;价值用实测(星级体系)

## 4. 星级体系(0-3 星,实测价值)

```
0 星 = raw 提炼的基础 wiki(全部新入库)
1 星 = ≥3 篇同星 wiki 高频共现(30 天窗口共现≥5 次,初始参数) → 结合调用上下文合成
2 星 = 同机制作用于 1 星层 → 触发异步翻译(短期不存在,翻译循环休眠)
3 星 = 封顶,不再向上合成
```

- **混层共现不升格,只喂养**:0 星新证据段落级并入 1 星(收敛优先于重跑);升格只能从纯同层群长出
- 防通胀:杜绝"1 星拉两篇 0 星凑 2 星";同一知识永远只有一份正本在长大
- 合成品**不豁免任何门控**:走完整内容质量循环 + 五闸
- 30 天无人调用的合成品降星归档,共现模式记负面案例
- 星级语义 = L4 红线;K/N/窗口参数 = L3

## 5. 架构裁决:脚本骨架 + LLM 函数 + Agent 在外

- **判定规则:节点内需要"自主决定下一步"才上 agent;固定变换一律 LLM 函数**
- Loop A 全部节点 = 固定变换:抓取/raw/准入/组装/gate/升格 = 脚本,提炼/复核 = LLM 函数(API 直调,litellm 路由,不经 agent 会话)
> **NOTE(2026-06-17 实测修订)**:本裁决待重估。实测+调研(Boris Cherny:"给模型目标让它爬坡到完成")表明 **repair 节点不该是固定变换**——它本质需要"自主决定怎么改、改到何处、何时停",正是该上 agent 的场景。把 repair 当脚本做(整页重写+逐字节 diff)是 addy 卡空转的根因。Plan 4 拟把 **驱动/收敛/修复三个控制面还权给模型(agent)**,门控/准入/五闸仍保持确定性脚本 fail-closed(知识库误放成本高,不照搬"harness 会贬值")。详见文末修订块。
- LLM 函数 = 固定输入→一次调用→schema 校验输出;重试/校验/预算全是确定性代码
- Agent 进场位置:修复循环(诊断开放式)、进化循环、源补充的找新源任务、治理的立法起草
- 状态:文件系统当队列 + jsonl 账本;幂等靠内容 hash;无数据库无消息队列

## 6. 循环规格模板(八要素 = 5 控制面 + 3 基座面)

```
控制面:①标准(机判) ②感知(自动度量偏差) ③驱动(AI 自生成提示词派活)
        ④收敛(定点修复,有界) ⑤裁决(独立 checker / 现实指标,maker≠checker)
基座面:⑥心跳(schedule/event/manual,宪法强制标注)
        ⑦状态(jsonl 账本:试过什么/过了什么/还开着什么;崩溃接续点)
        ⑧技能包(循环外置知识:量规/已知坑/模板——循环复利的载体)
附注:动作声明工具边界;并行写场景才加 worktree 隔离
```

计划中的循环没有八要素卡 = 设计未完成。

## 7. 七循环设计卡(全文见会话记录,此处为决策要点)

### 循环 1 内容质量(= 主链路本体,URL 进 → active 页 + 回链完成)
- 七段链:抓取→raw 锚点化→准入→提炼组装→门控→升格→收尾,**每段一检查点,前段不过后段不启动**
- 准入段新增:相关性/How 倾向/新颖度硬判定;负样本必须死在这里
- 评分器(grader):GPT-5.4 + 从样张反提取的量规(锚定/How 可执行/证据诚实/解读分离/密度),输出**点名缺陷清单**供定点修复
  > **NOTE(2026-06-17 实测修订)**:grader 本身实测可用(异族裁判、点名缺陷清单成立),**问题在 repair 侧而非 grader**。repair 空转 4 根因:① grader 的 location 词表 ≠ repair 小节定位 ② repair 只认 H2 不认 H3 ③ 整页重写+逐字节 diff 自相矛盾→整轮丢弃 ④ 超时静默吞(`repair.py:246`)。Plan 4(C+):repair 改 agent 爬坡,把 grader 的点名缺陷清单 + 黄金样本喂入,grader 复评作 `/goal` 停止条件。grader/量规零改动(forbidden)。
- 出厂标准(端到端口径):20 条 URL 语料(含 2 负样本),≥90% 正样本各段限轮走完全程,负样本 100% 拒于准入,样张 URL 重跑结构等价
- 运行期防漂移:周抽检 3 篇重过评分器,跌破阈值自动触发再校准
- 状态:`quality-loop.jsonl` 每篇一条生命线(七段判定+轮次+耗时+token)
- **质量循环是所有内容唯一入库出口**(含合成品/概念页),无第二条路径

### 循环 2 宪法治理
- 标准:全 vault 文件 100% 被规则认领;违法清单=0;法外内容 14 天内裁决
- **分诊**:违法(有规则,内容违反)→执法修内容;法外(无规则覆盖)→**优先立法**(修宪提案+Sync Impact Report,默许 24h)再迁移
- 立法提案必答:"这类内容为什么该存在于第二大脑"——答不出走 archive,防"给垃圾立法"
- 关键落地件:`claim-rules.yaml`(16 份标准编译成机读认领表,带来源条款号)
- 提案者与通过者不得同一 agent 会话;不变量修改 = L4

### 循环 3 星级体系
- 标准 = 机制自身有效性:合成品 30 天被调≥X 次比例≥70%;1 星集合被调率>0 星基线;误升率≤10%
- 合成 prompt 带共现时的调用上下文;约束"提炼共同模式产出母本没有的 how,拼接摘要必拒"
- 纯现实裁决:调用数据定星级存亡,模型自评只决定能否入库
- 状态:共现计数表 + 星级台账(升星依据/母本/30 天调用数)= 知识复利的资产负债表

### 循环 4 源质量汰换和补充
- 标准:每源 90 天滚动入库转化率≥5%;每领域≥2 活跃源
- 感知:四级漏斗(抓取→准入→五闸→被调),断在哪级诊断在哪级
- 找新源 = 真 agent 任务;**试抓 3 篇直接跑完整管线,管线即考官**
- 试用期 30 天;新源转正 L3 默许;领域 taxonomy 增删 = L4
- 状态:`sources-ledger.jsonl`(漏斗 + active/trial/throttled/retired 状态机)

### 循环 5 图谱健康
- 标准:orphan=0;pending 概念滞留≤14 天;hub 出度≤上限;高相似概念对必须有裁决记录
- ≥3 篇共指 pending 概念→建节点任务;新概念页走质量循环+gate 不豁免
- 建新概念 L3;概念合并(删节点)L4
- GRAPH-LINKING 标准现成,纯执行器

### 循环 6 检索效用(第二大脑主 KPI)
- 标准:查询命中率≥80%;落空查询 30 天内归因
- akb-search MCP 加查询日志(caller_id 预留给同事共享);**一份日志同时喂循环 3 和 6**
- 落空三分诊:(a)真没有→喂循环 4;(b)没召回→检索修复;(c)范围外→标记不折腾
- **历史落空查询 = 天然回归集**,修复后回放验证

### 循环 7 管线修复(全体循环的免疫系统)
- 标准:心跳按时率≥99%;节点失败率≤5%;**同一故障签名第 3 次出现时必须已有修复或已升级**
- 前提:全循环账本统一 jsonl 格式(七循环唯一强制共享物)
- 修复 agent(claude -p 无头)三档:S 静默(数据级)/B 分支(diff<50 行+不碰保护路径+测试绿,自动合并)/R 红线(提案人批)
- 故障签名 7 天不复现才关单;已修案例库(修复经验复利)
- 安全阀:token 预算上限;连修 2 败即停升级;watchdog 兜底

**通用性架构(2026-06-12 定稿):内核 + 适配卡(OS/驱动模式)**

- **通用内核**(与业务无关,写一次共用):账本+故障签名 schema、故障生命周期状态机(new→diagnosed→fixing→verifying→closed/escalated)、升级规则引擎(第 3 次必须已修或已升级/连修 2 败即停)、S/B/R 权限引擎+全局保护路径、watchdog、修复 agent 驱动器、已修案例库
- **修复适配卡**(每循环必须自带,内核拒绝无卡注册):故障签名表(错误类枚举)/ 诊断线索映射 / S 档动作白名单 / B 档可碰路径 / R 档红线 / 验证方法 / 回滚方法 / watchdog 配置行
- **设计纪律:新循环完整设计 = 八要素卡 + 修复适配卡**;缺适配卡不允许上线(候选入宪 v1.2)
- **契约先行、引擎后置**(对齐宪法"不过早抽象"):Plan 1 只落数据契约(schema + 适配卡格式 spec + 循环 1 适配卡 v1 + watchdog + 简化升级规则[第 3 次→SOD 简报]+ 案例库目录);修复 agent 驱动器等行为引擎留 Plan 4,届时已有 3+ 张真实适配卡检验契约表达力
- **Plan 1 循环 7 骨架五件**:①统一 jsonl 账本格式约定 ②failures.jsonl 故障签名记录 ③隔离区机制(与 FR-017 共生) ④watchdog 笨脚本 ⑤简化升级规则
- **星型协同拓扑(2026-06-12 补)**:卡与卡完全独立(互不引用,防 N² 网状耦合);跨循环协同全部由内核承担——①签名关联(故障传染:跨账本取证,同根因合并工单,修在根因循环、验证在表现循环)②共享依赖分组(适配卡增设"共享依赖声明"字段,内核按依赖去重报警:六循环报警→一个工单→修一次→各卡分别验证)③修复串行化(全局同时只跑一个修复,防动作撞车)
- **内核防腐门**:新循环设计发现内核缺能力时必须分诊"协议还是业务"——业务进卡永不进内核,协议升内核且契约带版本号(每张卡声明基于哪版契约);预期循环 2/5 零内核升级,循环 3/6 可能新增指标类签名
- **内核协同的五样内容(2026-06-12 补)**:①根因归属(工单挂给根因循环+修后两边联动复验)②共享依赖健康表(报警归并:六循环报警=一工单;依赖 down 时暂停各循环重试防风暴)③修复执行权(运行时全局串行 + 注册期静态路径冲突审查——唯一的卡间关系,发生在注册期由内核裁决)④修复经验(案例库按签名模式索引而非按循环,跨循环复用)⑤对人通知出口(升级事件单一汇报口,同根因绝不重复打扰)。协同的全部是横切面共享事实/资源,不含任何业务功能

## 8. 四环架构 + 自治分级

```
Ring 0 内容循环(时/天):循环1 + 翻译(休眠)
Ring 1 治理循环(周):循环2/3/4/5/6 的 schedule 部分
Ring 2 修复循环(事件):循环7
Ring 3 进化循环(月):功能架构自我迭代
```

**自治分级(默许制替代审批制,裁决权交现实,否决权留人,否决可选):**

| 级 | 范围 | 自治度 |
|----|------|--------|
| L0 | 内容入库 | 五闸全自动 |
| L1 | 数据级修复 | 静默,周报一行 |
| L2 | 代码 bugfix | 测试绿+金丝雀绿自动合并 |
| L3 | 能力进化(新源/新节点/prompt/参数) | 摘要预告 24h,无否决→金丝雀→指标裁决→自动转正/回滚 |
| L4 | 红线 | 提案制,必须人批 |

**L4 红线(短名单):** ①价值函数(gate 硬指标定义、星级语义)②安全边界(key/对外发布/花钱)③宪法本身+本红线清单
**信任阶梯**:L2 连续 20 次零回滚→放宽;回滚 2 次→升管制;红线清单逐季可收缩(挣来的)
**Ring 3 度量**:每个提案预声明指标,下月兑现核验,不兑现的提案类型降权
**Watchdog**:无 LLM 纯 shell ~50 行,每小时四环心跳/回滚率/账本检查,异常推手机;唯一不许进化的组件
**防漂移**:月度一致性审计(全新上下文 agent 只读宪法+代码,答"这还是宪法描述的系统吗")

## 9. 构建方式(loop 工程的本义)

- **用户给一次目标,/goal 机制驱动 agent 循环逼近,AI 自己给 agent 发提示词**
> **NOTE(2026-06-17 实测修订 · 范式分层)**:本节把"/goal 驱动循环"当成统一范式,概念错置。需分三层:(1)**dev 期构建循环**——/goal 驱动 agent 把 AKB2 这套系统造出来(本节描述的就是这层;本地 `/goal` 是提示词生成器,非 turn-loop,且无 `/loop` 命令);(2)**运行期内容循环(循环1)**——24h 常驻 daemon/launchd/watchdog,goal 达标即停**驱动不了**常驻供料,运行期是 loop 不是 goal;(3)**单篇 repair 收敛**——每篇向黄金样张爬坡,goal=量规阈值。三层不可混。详见文末修订块。
- GOAL 文件 = 机判验收标准(14 步清单 + 各循环①标准 + 出厂统计阈值)
- 构建循环:读账本→选工作单元→生成提示词→执行→pytest+gate+lint+样张回归→Codex cross-review→定点修复(有界)→记账→下一单元
- 用户出现两次:批计划(每 Plan 一次)、看收工报告
- 既定规则沿用:cross-review 走 Codex watch;/gd 并发 agent ≤2

## 13. F46 needs_repair 驻留通路(2026-07-12,用户明令)

### 背景
CONTENT-LIFECYCLE §2 早已定义 `needs_repair` 状态("有价值但未达 active 标准,留 staging,
修复后重新过门控"),但 runner 短路成 abort——repair 不收敛即永久出局。近 24h 数据:
~50 篇/天死于修复不收敛,同文重掷 grader 转正概率经验值 20-50%(replit 四掷两中)。
补齐后:不收敛候选驻留,低频重掷 grader+repair,收敛走正常门控入库,超龄淘汰。

### 预算(宪法 P1 有界,具名常量)
- `NEEDS_REPAIR_MAX_RETAKES = 3` —— 每篇一生最多 3 次重掷(驻留次数上限)。
- `NEEDS_REPAIR_MIN_INTERVAL_H = 20` —— 两掷间隔 ≥20h,让 grader 骰子跨会话。
- `NEEDS_REPAIR_PER_CYCLE = 4` —— 每轮主循环空闲期最多掷 4 篇(新文章优先,驻留池吃空闲)。F49 提速(2→4):驻留池 ~102 篇(07-16 账本实测),旧 2 篇/cycle 需 51 cycle 轮一遍,按主循环空闲期节奏约 20+ 天;提速 4 → 26 cycle,轮完周期减半。MAX_RETAKES/MIN_INTERVAL_H 不动。

### 停止条件
- 收敛 → 走完全链下游(A 层结构校验 → 硬门 → promote 五闸 → finalize,同函数同判定不开旁门),
  清理驻留文件。
- 3 次重掷耗尽 → 记 `abort`(reason=`needs_repair_expired`),清理驻留文件,恢复可被
  F26 requeue 手动重开(语义不变)。
- 驻留扫描异常 → catch + ledger `abort needs_repair`(reason=`residency_rethrow_error`),
  **不得杀死主循环**(7×24 daemon 生命线)。

### 分流边界(判定链零动)
非收敛分流只看 `failure_signature`:
- `distill_no_converge`(repair 跑完缺陷残留,内容性)→ needs_repair 驻留。
- 其余(`repair_route_failed`/`repair_worker_*` 子进程崩溃、`grader_all_down`/`grader_fallback_not_allowed`
  裁判宕机、`repair_idle_early_stop` 早停等过程性死亡)→ 现有 `abort` + F39 requeue(全链重跑)。
- `integrity_floor_failed`(不可补偿硬证)→ reject(不变)。
- 判定链零动:grader/floor/A 层/五闸/promote 全不碰,驻留只给"再掷一轮"的入口。

### 与 F26 requeue 的区别
| 维度 | F26 requeue | F46 needs_repair 驻留 |
|------|------------|----------------------|
| 触发 | infra 死亡(裁判宕机/worker 崩溃)自动 1 次;或手动 CLI | 内容不收敛(repair 跑完缺陷残留)自动驻留 |
| 重跑范围 | 全链重跑(admission→提炼→评分→修复) | 只重跑 grader+repair(从 final_text 续,不重新 intake/提炼) |
| 进度 | 推倒重来 | 已修好的不推倒(final_text 持久化 `<staging>/needs-repair/<hash>.md`) |
| 预算 | 一生 1 次(AUTO_INFRA_REQUEUE_MAX=1) | 一生 3 次(NEEDS_REPAIR_MAX_RETAKES=3),间隔 ≥20h |
| 终态 | 重审产生新终态(可再 requeue) | 收敛→finalize / 超龄→expired abort(后可被 F26 requeue 手动重开) |

### _is_processed 三态语义
主扫描(`_scan_queue`)跳过:终态(finalize/abort 无后续 requeue) OR 驻留中(needs_repair 无后续终态)。
驻留 hash `_is_resident=True`(由驻留扫描接管);终态 hash `_is_resident=False`;未处理 both=False。
