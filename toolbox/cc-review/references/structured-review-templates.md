# 结构化审查模板

这些模板供 `cc-review` 使用。

最终回复外层规则：所有用户可见审查结果必须放在单个 fenced `markdown` code block 内，code block 外不得有任何普通说明。

## 中文输出规则

当用户使用中文时，最终用户可见输出必须使用中文模板：

- 标题、章节名、字段名、结论值、审查范围值、表格状态值、空结果、检查面名称都必须中文。
- 英文只允许作为技术证据出现：文件路径、命令、函数名、变量名、配置 key、源材料中的枚举原值、日志原文、报错原文、第三方产品名。
- 如果没有问题或剩余风险，写 `无`。

## 固定翻译映射

### 审查领域

- `ai_infra` -> `AI 基础设施`
- `app_code` -> `应用代码`
- `docs_content` -> `文档内容`
- `other` -> `其他`

### 审查模式

- `single_pass` -> `单轮`

### 审查范围

- `full_matrix` -> `全局矩阵`
- `prior_findings_only` -> `仅前序问题`
- `direct_downstream` -> `直接下游`
- `user_expanded` -> `用户扩展`

### 状态值

- `pass` -> `通过`
- `fail` -> `失败`
- `n_a` -> `不适用`

### AI 基础设施检查面

- `runtime active` -> `运行状态`
- `mirror backup` -> `镜像备份`
- `trigger surface` -> `触发表面`
- `generation surface` -> `生成表面`
- `state/baseline` -> `状态与基线`
- `validation/runtime health` -> `验证与运行健康`
- `stale/dormant cleanup` -> `陈旧与休眠清理`

### 应用代码检查面

- `changed files` -> `变更文件`
- `API/contracts` -> `接口与契约`
- `data/schema` -> `数据与结构`
- `state/concurrency` -> `状态与并发`
- `UI/UX` -> `界面与体验`
- `tests` -> `测试`
- `security/performance` -> `安全与性能`
- `deployment/runtime` -> `部署与运行`

### 文档内容检查面

- `source material` -> `来源材料`
- `generated output` -> `生成结果`
- `links/assets` -> `链接与资产`
- `metadata` -> `元数据`
- `publish path` -> `发布路径`
- `policy/compliance` -> `政策与合规`
- `validation` -> `验证`

## 领域矩阵

`审查领域` 决定内部检查覆盖。最终输出的 `已检查范围` 只列 3-5 个关键检查面，不输出完整矩阵。

- `AI 基础设施`：运行状态、镜像备份、触发表面、生成表面、状态与基线、验证与运行健康、陈旧与休眠清理
- `应用代码`：变更文件、接口与契约、数据与结构、状态与并发、界面与体验、测试、安全与性能、部署与运行
- `文档内容`：来源材料、生成结果、链接与资产、元数据、发布路径、政策与合规、验证
- `其他`：审查者必须说明实际检查的 3-5 个维度

## 计划审查模板

用于计划、PRD、方案、实施策略、以及“计划审查”。

### 计划审查对齐

审查使用 Codex 可执行计划模板的计划时：

- 先读取计划的 `Review 对齐` 章节。
- 如果计划声明 `REVIEW_DOMAIN`，按固定映射翻译为中文 `审查领域`；除非它明显不匹配当前产物。
- 如果覆盖计划声明的领域，在 `已检查范围` 中说明原因。
- 如果计划声明 `REVIEW_FOCUS`，优先把这些项翻译成中文检查面并作为第一批检查行。
- 检查计划的领域备注是否覆盖相关领域矩阵维度。
- 可执行实施计划缺少 `Review 对齐` 且会导致审查范围漂移时，作为计划缺口报告。
- 不要因为非选中领域写 `无` 就制造问题；只有 P1/P2 需求、运行路径、数据/安全风险或核心验证缺失才进入 `问题`。

```markdown
# 计划审查结果

结论：通过 | 需要修改
审查领域：AI 基础设施 | 应用代码 | 文档内容 | 其他
审查模式：单轮
审查范围：全局矩阵 | 仅前序问题 | 直接下游 | 用户扩展

## 已检查范围

| 检查面 | 结论 | 证据 |
|--------|------|------|
| <最多 3-5 个关键检查面，优先使用计划里的 REVIEW_FOCUS 并翻译成中文> | 通过/失败/不适用 | <简短证据> |

## 问题

### 问题 1 [P1|P2] <标题>

问题：<会导致目标失败的计划缺口>
证据：<计划段落/路径/命令>
影响：<按当前计划执行会出什么问题>
最小修复：<需要补充什么，不扩大范围>
验收：<如何确认修复有效>

## 剩余风险

<P3 或非阻塞项；没有则写“无”>
```

## 代码审查模板

用于已完成工作、diff、变更文件、实现结果、final review、以及“代码验收”。

```markdown
# 代码审查结果

结论：通过 | 需要修改
审查领域：AI 基础设施 | 应用代码 | 文档内容 | 其他
审查模式：单轮
审查范围：全局矩阵 | 仅前序问题 | 直接下游 | 用户扩展

## 已检查范围

| 检查面 | 结论 | 证据 |
|--------|------|------|
| <最多 3-5 个关键检查面> | 通过/失败/不适用 | <简短证据> |

## 问题

### 问题 1 (<文件>:<行号>) [P1|P2] <标题>

问题：<当前代码中的明确缺陷>
证据：<文件:行号/命令输出/隔离复现>
影响：<哪个活跃路径失败，或哪项验证不可靠>
最小修复：<需要修改的文件/函数/配置>
验收：<可执行命令或隔离测试>

## 剩余风险

<P3 或非阻塞项；没有则写“无”>
```

## 严重度与收敛规则

- P1：当前目标失败、数据/安全/不可逆风险、或核心验证缺失。
- P2：重要需求或活跃行为可能回归。
- P3：陈旧文档、休眠代码、镜像漂移、清理风险；只放入 `剩余风险`，不进入阻塞问题。
- `需要修改` 只用于阻塞级别：活跃路径失败、目标不满足、数据/安全风险、核心验证缺失。
- 不要因风格偏好、架构审美、休眠代码、不影响运行的陈旧文档、非活跃路径清理、无失败证据的潜在优化而阻塞。
- 后续审查默认只查 `仅前序问题` 或 `直接下游`。
- 后续审查窄例外：只有同时满足以下条件的新问题才允许加入：P1/P2 阻塞、由当前 diff 引入、证据中说明 `changed_in_this_round` 和 `why_not_scope_creep`。
- 同一根因最多阻塞 2 轮；之后剩余项放入 `剩余风险`。
