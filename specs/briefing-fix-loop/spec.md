# Feature Specification: Briefing 审计-定点修复收敛循环

**Created**: 2026-06-10
**Status**: Draft
**Input**: 用户描述：将 briefing 流水线「审计失败 → 整篇丢弃 → 次日全链路重跑」改为「审计发现可定位缺陷 → 针对被点名字段定点修复 → 重新审计，直到收敛或触上限」。（点 1，源自 Loop engineering 大小循环讨论）

## 背景与现状

briefing 流水线当前是**线性**的：采集 → 打分 → 合成 → 结构门控 → 翻译 → 译后审计 → 发布。译后审计会产出**可定位的缺陷清单**（如「执行摘要无中文」「第 3 条推文的中文点题缺失」「某数字/工具名译错」）并给出 `pass | warn | fail` 裁决。

现状的问题：这份缺陷清单**只用来出裁决，随后被丢弃**。裁决为 `fail` 时整篇简报留在 staging，由次日补跑守卫把**整条流水线从采集开始重跑**——重新抓推文、重新打分、重新合成、重新翻译——只为修一个局部的翻译缺陷，且靠重跑碰运气。

本 feature 把审计缺陷清单从「一次性裁决依据」变为「修复回路的输入」：只重做被点名的局部，反复审计直到达标或触上限。对齐 `docs/constitution.md` 原则 2（收敛优先于重跑）、原则 1（有界自动化）、原则 3（Fail-Closed 质量门控）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 局部翻译缺陷被定点修复后入库 (Priority: P1)
某日简报合成与翻译完成后，审计发现少数局部翻译缺陷（如执行摘要漏翻中文、个别推文 zh_point 缺失），但整体内容正确。系统针对这些被点名的字段重新翻译，重新审计；缺陷清空后该简报正常入库，无需重跑上游采集/打分/合成。

**Why this priority**: 这是最高频、最该自动化的场景——现状下这类局部缺陷会导致整篇被丢、当日可能无简报。修复它直接消除「为一个漏翻标题丢一整天产出」的浪费。

**Independent Test**: 构造一份「上游内容正确、仅含可定位翻译缺陷」的合成产物，跑修复循环，验证：缺陷被逐条修复、最终审计为 `pass`、且过程中未触发任何上游采集/打分/合成动作。

**Acceptance Scenarios**:
1. **Given** 译后审计返回 `accuracy_issues` 含「执行摘要无中文」, **When** 修复循环执行, **Then** 仅执行摘要被重新翻译，其余字段不变。
2. **Given** 第 1 轮修复后审计仍报 1 处剩余缺陷, **When** 进入第 2 轮, **Then** 仅剩余那处被再修，已达标字段不重复处理。
3. **Given** 某轮修复后审计返回零缺陷, **When** 循环检查收敛条件, **Then** 循环立即结束，简报以 `pass` 入库。

### User Story 2 - 触达修复上限后 fail-closed (Priority: P1)
某日缺陷在允许的最大修复轮次内仍未清零（如反复重译仍无法消除漂移）。系统停止修复，不入库，把产物留在 staging 并把最终裁决写入 frontmatter，供人工或后续补跑处理。

**Why this priority**: 没有上限的修复会无界烧 LLM 额度（违反原则 1）；触上限必须有明确的 fail-closed 落点（原则 3），否则会出现「永远在修、永不发布」或「带病入库」。

**Independent Test**: 构造一份「审计每轮都会报至少 1 处缺陷」的产物，验证循环在到达上限轮次后停止、产物未入库（留 staging）、frontmatter 记录了最终裁决与触上限事实。

**Acceptance Scenarios**:
1. **Given** 修复已执行到约定的最大轮次且审计仍非 `pass`, **When** 循环检查收敛条件, **Then** 停止修复、不入库、产物留 staging。
2. **Given** 触上限停止, **When** 写入产物 frontmatter, **Then** 记录最终 `audit_verdict` 与「修复触上限」标记，可被补跑守卫与人工识别。

### Edge Cases
- **纯结构缺陷（非局部可修）**：审计的 `standard_issues` 指向结构性问题（如整体未翻译、字段缺失到无法定点），定点修复无意义 → 此类缺陷不进入逐字段修复回路，直接按现有门控 fail-closed。
- **修复引入新缺陷**：某轮修复后审计发现的缺陷数不降反升 → 仍受最大轮次约束；不得因「越修越糟」陷入无界循环。
- **审计能力不可用**（LLM 审计降级/跳过）：无法产出可定位缺陷清单时 → 不进入修复回路，按现有降级路径处理，不得空转。
- **部分修复**：触上限时若已修复部分缺陷 → 最终裁决与 frontmatter 必须反映真实剩余缺陷，不得报「已修复」掩盖残留（原则 4：失败可见）。

## Requirements *(mandatory)*

### Functional Requirements
- **FR-001**: 系统 MUST 把译后审计产出的可定位缺陷清单作为修复输入消费，不得在出裁决后丢弃。
- **FR-002**: 修复动作 MUST 仅作用于被审计点名的字段，MUST NOT 触发上游采集、打分、合成的重做。
- **FR-003**: 修复-审计回路 MUST 有显式最大轮次上限；达上限即停止（对齐原则 1）。
- **FR-004**: 每轮修复后系统 MUST 重新审计，并以「审计缺陷清单为空」作为收敛（成功结束）条件。
- **FR-005**: 当回路因收敛而结束时，简报 MUST 按 `pass` 正常入库。
- **FR-006**: 当回路因触上限而结束且仍未达标时，简报 MUST NOT 入库（留 staging），且最终裁决 MUST 写入产物 frontmatter（对齐原则 3）。
- **FR-007**: 对无法定点修复的结构性缺陷，系统 MUST 跳过修复回路并走 fail-closed 门控，MUST NOT 空转。
- **FR-008**: 触上限时的部分修复结果 MUST 在产物与日志中如实反映剩余缺陷，MUST NOT 以「成功」掩盖残留（对齐原则 4）。
- **FR-009**: 修复回路的每轮缺陷数、最终结束原因（收敛 / 触上限）MUST 可从日志观测（对齐原则 4）。

### Key Entities *(涉及数据时)*
- **审计缺陷清单**：一次审计产出的可定位缺陷集合，区分「可定点修复的局部缺陷」与「结构性缺陷」；每条缺陷可定位到具体字段。
- **简报产物**：待审计/待发布的简报内容，携带门控裁决与审计裁决元数据；其落点（staging vs 入库）由本 feature 的收敛结果决定。
- **修复回路状态**：当前轮次、本轮待修缺陷、累计结束原因；用于判定收敛与上限。

## Success Criteria *(mandatory)*

### Measurable Outcomes
- **SC-001**: 对「上游内容正确、仅含局部翻译缺陷」的简报，因这类缺陷导致的「当日 0 简报」发生率降到 0——这类简报经修复后入库，不再被整篇丢弃。
- **SC-002**: 修复一个局部缺陷的过程 0 次触发上游采集/打分/合成重做（可由该次运行的阶段调用记录验证）。
- **SC-003**: 修复回路在任意输入下都在约定最大轮次内终止，无一例无界运行（可由日志的「结束原因」字段全覆盖验证）。
- **SC-004**: 触上限未达标的简报 100% 留在 staging 且未进入知识库（可由入库落点与 frontmatter 裁决一致性验证）。
- **SC-005**: 每次修复回路的最终裁决与「实际剩余缺陷数」一致，无「报 pass 但仍有缺陷」的样本（对齐原则 4）。

## Assumptions
- 译后审计已能产出**结构化、可定位到字段**的缺陷清单（含局部翻译类与结构类的区分）——此为现状已具备的能力。
- 系统已具备对**单个译文字段做局部重译**的能力，无需重译整篇。
- 最大修复轮次取一个小常量（建议 2–3 轮）；具体值在 `/gd plan` 阶段定，按「按次数」预算约定声明（对齐原则 4 单位一致性）。
- 「收敛」以审计缺陷清单为空为准；warn 级裁决是否视为可入库沿用现有 enforcement matrix（`warn` 入库但标记），本 feature 不改门控枚举语义。
- 本 feature 不改外层触发（launchd / 补跑守卫）；补跑守卫的必要性在本 feature 上线后另行评估（与点 1 讨论一致）。

## 与 constitution 的对齐
- 原则 1 有界自动化：FR-003 强制最大轮次上限。
- 原则 2 收敛优先于重跑：FR-001/FR-002 把缺陷清单变修复输入、禁止上游重做。
- 原则 3 Fail-Closed 质量门控：FR-006 触上限不入库 + 裁决可追溯。
- 原则 4 预算显式/失败可见：FR-008/FR-009 + SC-005 要求残留与结束原因可见。
