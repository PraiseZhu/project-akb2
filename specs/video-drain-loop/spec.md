# Feature Specification: Video 研究待办队列单次清空循环

**Created**: 2026-06-10
**Status**: Draft
**Input**: 用户描述：video 研究链路当前把失败项攒进待办队列、靠下一次定时跑被动重试（卡住的视频可能拖几天）。改为：单次触发内主动清空待办队列直到队列空或预算耗尽，失败项计数保留且不阻塞其余项。（点 2，源自 Loop engineering 大小循环讨论）

## 背景与现状

video 研究链路把每个待研究视频逐个处理；遇到失败（额度耗尽、网络错误等）会把该视频记入待办队列并累加重试计数，成功的则移出队列。

现状的问题：待办队列的**消费是被动的**——一个失败/未完成的视频要等**下一次定时触发**才会再轮到，而该链路没有专属定时触发（当前为手动/命令行触发），导致一个卡住的视频可能拖好几天才被再试一次。单个视频内部虽有「轮询等待研究产物」的等待循环，但**跨视频没有「一次触发内尽量把队列清空」的回路**。

本 feature 在单次触发内引入「清空回路」：循环消费待办队列直到队列空或触达显式预算上限；每项处理成功则移出、失败则计数保留并继续下一项。对齐 `docs/constitution.md` 原则 1（有界自动化）、原则 4（预算显式/失败可见）、自动化纪律（触发器分类 + 可观测）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 单次触发内清空可处理的待办 (Priority: P1)
触发一次 video 研究后，待办队列里有若干视频。系统在本次触发内逐个处理，成功的移出队列，直到队列清空（或预算耗尽）。不再出现「本次只处理一批、剩下的等下次」的被动拖延。

**Why this priority**: 这是本 feature 的核心价值——把「卡住的视频拖几天」压缩到「一次触发内尽量清完」。

**Independent Test**: 构造一个含 N 个可处理视频的待办队列，在充足预算下触发一次，验证队列被清空（成功项全部移出）、且处理在单次触发内完成而非跨多次触发。

**Acceptance Scenarios**:
1. **Given** 待办队列有 N 个可处理视频且预算充足, **When** 触发一次清空回路, **Then** N 个全部被处理并移出队列，队列变空。
2. **Given** 队列处理过程中某项成功, **When** 继续下一项, **Then** 已成功项不再被重复处理。

### User Story 2 - 失败项计数保留且不阻塞队列 (Priority: P1)
处理过程中某个视频因额度/网络等原因失败。系统为它累加重试计数并保留在队列中，然后**继续处理队列里的其余视频**，不因一个失败项中断整次清空。

**Why this priority**: 若一个失败项能阻塞后续，单点故障会拖垮整次清空；失败隔离是队列清空可用的前提。

**Independent Test**: 构造队列含 1 个必然失败项 + 若干可成功项，触发一次，验证：失败项重试计数 +1 且仍在队列、其余可成功项全部被处理并移出。

**Acceptance Scenarios**:
1. **Given** 队列中某项处理失败, **When** 回路处理该项后, **Then** 该项重试计数 +1 且保留在队列，不被移出。
2. **Given** 某项失败后, **When** 回路继续, **Then** 队列其余项照常被处理，不被该失败中断。
3. **Given** 某项重试计数已达约定上限, **When** 回路遇到它, **Then** 按约定处理（跳过/标记），不无限重试同一项。

### User Story 3 - 预算耗尽时部分完成且如实上报 (Priority: P2)
队列较长或额度受限，本次触发在清空前触达预算上限。系统停止本次清空，把已完成与剩余未处理项如实记录，剩余项留在队列等下次触发。

**Why this priority**: 无界清空会烧光额度（违反原则 1）；预算耗尽属正常路径，必须显式上报「清了多少、剩多少」而非伪装成功（原则 4）。

**Independent Test**: 给一个明显超出单次预算的队列，触发一次，验证：回路在预算耗尽时停止、日志/结果明示「已处理 X / 剩余 Y」、剩余项仍在队列。

**Acceptance Scenarios**:
1. **Given** 队列规模超过单次预算可处理量, **When** 预算耗尽, **Then** 回路停止，剩余未处理项保留在队列。
2. **Given** 预算耗尽停止, **When** 汇报本次结果, **Then** 明示已处理数与剩余数，不报「全部完成」（对齐原则 4）。

### Edge Cases
- **空队列触发**：触发时队列已空 → 回路立即结束，不产生空转或误报。
- **预算为 0 / 极小**：至多处理 0 个就停止并如实上报，不得违反预算上限。
- **单视频内部等待超时**：单项的「等待研究产物」超时属该项失败，按失败项处理（计数 + 继续），不拖垮整次清空。
- **回路自身耗时统计**：预算判定以可观测的耗时/资源为准，确保「预算耗尽」是真实触达而非估算（原则 4）。

## Requirements *(mandatory)*

### Functional Requirements
- **FR-001**: 单次触发 MUST 循环消费待办队列，直到队列清空或触达预算上限才结束。
- **FR-002**: 每项处理成功 MUST 将其移出队列；失败 MUST 累加其重试计数并保留在队列。
- **FR-003**: 单个失败项 MUST NOT 中断本次清空回路对其余项的处理（失败隔离）。
- **FR-004**: 清空回路 MUST 受显式、具名的预算上限约束（时间/资源），MUST NOT 无界运行（对齐原则 1、原则 4 预算显式）。
- **FR-005**: 重试计数达约定上限的项 MUST 按约定处理（跳过或标记），MUST NOT 无限重试同一项。
- **FR-006**: 因预算耗尽而结束时，系统 MUST 如实上报「已处理数 / 剩余数」，MUST NOT 报「全部完成」（对齐原则 4 失败可见 / 部分失败明示）。
- **FR-007**: 本次清空的结束原因（队列空 / 预算耗尽）、处理与剩余计数 MUST 可从日志观测。
- **FR-008**: 空队列触发 MUST 立即正常结束，MUST NOT 空转或误报。

### Key Entities *(涉及数据时)*
- **待办队列项**：一个待研究视频的待办记录，含其标识与重试计数；处理成功移出，失败计数 +1 保留。
- **清空回路预算**：本次触发允许消耗的上限（时间/资源），具名声明；触达即停止。
- **清空结果**：本次触发的结束原因、已处理数、剩余数；用于上报与下次触发的起点。

## Success Criteria *(mandatory)*

### Measurable Outcomes
- **SC-001**: 在预算充足时，一个可处理的待办视频在**单次触发内**被处理完，不跨天/不等下次触发（可由「触发次数=1 时队列清空」验证）。
- **SC-002**: 队列中存在失败项时，其余可处理项的完成率不受影响（可由「失败项保留 + 其余项全部移出」验证）。
- **SC-003**: 清空回路在任意队列规模下都在预算上限内终止，无一例无界运行（可由日志结束原因字段全覆盖验证）。
- **SC-004**: 预算耗尽的每次触发都给出「已处理 X / 剩余 Y」且与队列实际一致，无「报全完成但仍有剩余」的样本（对齐原则 4）。
- **SC-005**: 同一失败项的重试次数不超过约定上限（可由该项重试计数封顶验证）。

## Assumptions
- 待办队列与重试计数机制为现状已具备的能力；本 feature 增加的是「单次触发内主动清空」的回路，不是新的队列存储。
- 预算上限沿用 video 链路既有的「按时间」预算约定（与现有视频处理总预算同一单位），具体秒数在 `/gd plan` 定（对齐原则 4 单位一致性）。
- 重试计数上限取一个小常量；具体值在 `/gd plan` 定。
- 本 feature 不新增定时触发器（不擅自注册 plist，对齐自动化纪律）；触发方式维持现状（手动/命令行），是否升级为定时触发由用户另行决定。
- 单视频内部的「等待研究产物」等待逻辑维持现状，本 feature 只在其外层加跨视频的清空回路。

## 与 constitution 的对齐
- 原则 1 有界自动化：FR-004 强制显式预算上限。
- 原则 4 预算显式/失败可见：FR-004/FR-006/FR-007 + SC-003/SC-004 要求预算具名、部分完成明示、结束原因可见。
- 自动化纪律：Assumptions 明确不擅自注册定时触发器、维持手动触发分类、要求可观测。
